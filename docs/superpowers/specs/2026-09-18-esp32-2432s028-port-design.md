# Port: ESP32-2432S028 ("Cheap Yellow Display")

Design for an eighth board port, targeting the widely-available
ESP32-2432S028 development board. This is the first port to a board that is
not an ESP32-S3 or ESP32-C6, and the first to use a resistive touch panel.

## Hardware

Verified over `esptool flash_id` on the connected unit:

- **SoC**: ESP32-D0WD-V3, dual-core Xtensa, revision v3.1, 40 MHz crystal
- **Flash**: 4 MB
- **PSRAM**: none (`Features:` reports only `WiFi, BT, Dual Core, 240MHz`)

The remaining details come from the widely-documented 2432S028 pin map and
must be confirmed on hardware during bring-up:

- **Display**: ILI9341, 240×320 native, driven in landscape as 320×240.
  4-wire SPI on its own bus: `MOSI=13, MISO=12, SCLK=14, CS=15, DC=2`. The
  panel reset is not broken out to a GPIO (tied to the module reset), so the
  driver is constructed with `GFX_NOT_DEFINED` for reset. Backlight is
  `GPIO 21`, driven as LEDC PWM because the ILI9341 exposes no brightness
  command — identical in shape to the LCD-1.54 port's ST7789 handling.
- **Touch**: XPT2046 resistive controller on a *separate* SPI bus
  (`CLK=25, MOSI=32, MISO=39, CS=33, IRQ=36`). Because the two buses are
  physically distinct, there is no contention with the display and no need to
  share a bus lock.
- **No PMU, no IMU, no battery circuit, no IO expander.** The board is USB
  powered.
- **Buttons**: the onboard BOOT button on `GPIO 0` is the only usable user
  button. There is no second button and no PWR-role button (the other
  onboard button is EN/reset).

Some 2432S028 batches ship an ST7789 panel instead of an ILI9341, and some
ship a capacitive (CST820) touch panel instead of the resistive XPT2046.
This port targets the resistive ILI9341 variant that is connected; the
display driver choice is the first thing to re-check if the panel stays dark.

## Capability profile

The board's feature set is the sparsest in the tree, and every gap already
has an established precedent:

| Capability | Value | Precedent |
|------------|-------|-----------|
| PSRAM | absent | the two C6 ports |
| Battery / PMU | absent | `waveshare_lcd_4` |
| IMU / rotation | absent | `waveshare_lcd_4` |
| Secondary button | absent | `waveshare_lcd_4` |
| PWR button | absent | `waveshare_lcd_4` |
| Sound | absent | `waveshare_lcd_4` |
| SPI TFT + PWM backlight | present | `waveshare_lcd_154` |

Consequently no shared code changes are required. Omitting `BOARD_HAS_PSRAM`
selects the existing internal-SRAM paths: 20-line LVGL draw buffers in
`main.cpp`, direct-draw splash rendering in `splash.cpp`, the static corner
mascot in `ui.cpp`, and an unsupported `screenshot` serial command.

## What is genuinely new

Three things have no existing analogue in the tree and carry the risk:

**1. A non-S3, non-C6 SoC.** The PlatformIO env targets `board = esp32dev`
with no `board_build.arduino.memory_type` (that setting is S3 PSRAM-specific).
The classic ESP32 has no native USB, so `ARDUINO_USB_CDC_ON_BOOT` must be
omitted entirely — `Serial` is plain UART0 over the onboard CP2102 bridge.
Flashing and monitoring therefore use `/dev/cu.usbserial-*` rather than the
`/dev/cu.usbmodem*` path every other port documents.

**2. Resistive touch.** Every existing port reads a capacitive controller
over I2C, which reports coordinates already in pixel space. The XPT2046
returns raw 12-bit ADC readings that must be mapped to pixels through
per-unit calibration constants, and the readings are noisy enough that the
driver must median-filter several samples per report. The port vendors a
minimal XPT2046 SPI reader rather than taking a dependency, consistent with
the project's existing practice of vendoring small touch readers to avoid
copyleft libraries. Calibration bounds are defined as named constants in
`board.h` so they can be tuned in one place after eyeballing raw values on
hardware.

**3. A 4 MB flash budget.** Every other port has 8 or 16 MB. The default
4 MB partition layout gives the app only ~1.3 MB, which this firmware will
not fit — the splash animation table alone is roughly 400 KB on top of LVGL,
NimBLE and the bitmap fonts. The env therefore selects `huge_app.csv`
(~3 MB app). If the image still overflows, the fallback is to trim the
animation set for this board rather than to change shared code.

## Layout and orientation

The panel runs landscape at 320×240, set through the ILI9341 driver's
rotation parameter rather than by CPU pixel remapping (the ILI9341's MADCTL
supports a true row/column exchange, unlike the CO5300 that forced the 2.16"
port into software rotation). Rotation is fixed at construction; there is no
IMU and no runtime rotation.

At 240 px high the board falls under the existing `H >= 460` breakpoint in
`compute_layout()`, so it inherits the compact layout already used by the
240×240 LCD-1.54 port. The extra 80 px of width relative to that port is
slack, not a new breakpoint, so no `ui.cpp` change is expected. This
assumption gets checked visually during bring-up.

## Files

A new `firmware/src/boards/cyd_2432s028/` folder holding the standard
per-board set (`board.h`, `board_init.cpp`, `display.cpp`, `touch.cpp`,
`input.cpp`, `power.cpp`, `imu.cpp`, `sound.cpp`, `caps.cpp`), plus one new
`[env:cyd_2432s028]` block in `firmware/platformio.ini`. No shared file is
modified except documentation: `CLAUDE.md` and
`docs/porting/adding-a-board.md` both currently state that an ESP32-S3 with
OPI PSRAM is required, which this port disproves and should correct.

## Verification

The board is connected, so every step is checked on real hardware rather
than asserted:

1. `pio run -e cyd_2432s028` links cleanly and the image fits the partition.
2. Flash and watch `pio device monitor` for the per-subsystem init lines
   every port logs during `setup()`.
3. The splash screen renders, and the Clawd animation plays at an acceptable
   frame rate through the direct-draw path.
4. Touch: verify raw ADC ranges by logging, set the calibration constants,
   then confirm a tap lands where expected by exercising the splash/usage
   screen toggle in all four corners.
5. BOOT button sends HID Space over BLE.
6. BLE pairs with the host daemon and a usage payload renders.

The `screenshot.sh` route is unavailable (no PSRAM), so visual QA is by
direct observation of the panel.
